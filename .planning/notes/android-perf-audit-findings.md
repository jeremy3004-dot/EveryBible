# Android Performance Audit — Findings

**Ran:** 2026-06-11 · 4 parallel codebase auditors (lists, render/nav, native/startup, animations/overdraw)
**Question:** Why is EveryBible slow/janky on older low-end Android phones? (focus: scroll + nav)

## Headline diagnosis

The felt slowness is **NOT GPU/blur** — the suspected #1 offender (expo-blur "liquid glass")
turns out to **not be rendered anywhere** in the app. The real cause is a **JS-thread re-render
storm**: the app rebuilds large React trees many times per second during the two activities users
do most — **listening with follow-along** and **scrolling the reader**. On a weak CPU each of those
re-renders is slow, so the JS thread can't keep up and frames drop. Two structural issues compound
it: the **Android release build ships unminified**, and one **flagship list isn't virtualized**.

Good news: Hermes is on, the cold-start path is genuinely well-optimized, MMKV is fully applied,
and the core Bible lists are already on FlashList. The problems are concentrated, not systemic.

## Prioritized findings

### TIER 1 — Critical

#### P1. Audio-position render storm in the Bible reader  ·  scroll + playback jank  ·  M–L
`useAudioPlayer` subscribes to `currentPosition`, which ticks every 250ms (`useAudioPlayer.ts:32,102-108,479-488`;
`audioStore.ts:132-139`). Every consumer of the hook re-renders 4–8×/sec while audio plays. The biggest
consumer is the ~5,800-line `BibleReaderScreen` (`BibleReaderScreen.tsx:942-967`), and because its
`renderItem`/`renderParagraph` are inline closures with inline `style` arrays and **zero `React.memo`**
(`:4626,4716`), the entire chapter's verse cells re-reconcile on every tick. This is the dominant jank
source during follow-along.
**Fix:** (a) split `useAudioPlayer` into `useAudioControls()` (discrete fields + actions, no position) and a
leaf `useAudioPosition()`; (b) consume live position only in a small memoized leaf / drive the active-verse
highlight via a Reanimated shared value instead of React state; (c) extract a top-level `React.memo`
`ReaderParagraph` with `StyleSheet`-only styles + stable `useCallback` `renderItem`; memo `HighlightedVerseText`.
**Measure:** React DevTools Profiler — screen body & paragraph rows should show ~0 re-renders/sec while audio
plays idle; JS FPS holds ~60 on a 3GB device.

#### P2. Android release build ships UNMINIFIED (R8/ProGuard + resource shrinking OFF)  ·  baseline + cold start + RAM  ·  M
`android/` is gitignored and regenerated by EAS prebuild, and there's no `expo-build-properties` plugin
(`app.json:52-79`), so R8/ProGuard and `shrinkResources` stay at Expo's default (off). The production AAB
ships unminified, untree-shaken DEX with all unused classes/resources → larger install, more DEX to verify/load,
higher baseline RAM, slower class loading at launch.
**Fix:** add `expo-build-properties` with `android.enableProguardInReleaseBuilds: true` +
`enableShrinkResourcesInReleaseBuilds: true`; supply `proguard-rules.pro` keep rules for reflection-based libs
(Reanimated, MMKV, Supabase/Gson, google-signin); smoke-test a release AAB for missing-class crashes.
**Measure:** AAB size + cold-start TTI (`adb logcat | grep "Displayed com.everybible.app"`) before/after.

### TIER 2 — High

#### P3. Scroll-collapse chrome runs as a JS-thread animation during scroll  ·  scroll + nav lag  ·  M
`ReaderPlaybackDock` receives the React **useState** number `readerBottomChromeProgress` instead of the
SharedValue, so its worklets only update via re-render — and the scroll handler `runOnJS`-writes that state
~50× per collapse (`BibleReaderScreen.tsx:704,1664,4845`; `ReaderPlaybackDock.tsx:79-110`). On top of that,
the same scroll callback fires `navigation.setOptions`/`setParams` + `LayoutAnimation` on every ~0.02 step
(`:766-793`), reconciling the tab navigator tens of times per collapse.
**Fix:** pass the SharedValue (`readerBottomChromeProgressShared`) into the dock and read `.value` in worklets;
drive the tab bar via a shared value + `useAnimatedStyle`; only call `setOptions`/`setParams`/`LayoutAnimation`
on the discrete collapsed↔expanded transition, not per step.
**Measure:** JS FPS while collapsing chrome mid-scroll; navigator re-renders per collapse ≤2.

#### P4. PlanDetailScreen renders up to 365 day cards non-virtualized in a ScrollView  ·  scroll + slow open  ·  M
`visibleDayNumbers.map(...)` inside a plain `<ScrollView>` mounts every `DayRow` (not memoized) at once
(`PlanDetailScreen.tsx:362,857,953`; `readingPlanModel.ts:153`). "Bible in a Year" = 365 mounted rows — slow
to open and janky to scroll. Only bites fixed-length plans, but those are the flagship plans.
**Fix:** replace with `FlashList` (already a dep), `estimatedItemSize ~96-120`, memoized `renderItem`,
`React.memo` `DayRow`; keep cover/related as `ListHeaderComponent`/`ListFooterComponent`.
**Measure:** mounted `DayRow` count ~10 (not 365); open TTI < 300ms on a 3GB device.

### TIER 3 — Medium

#### P5. FieldCard overdraw + perpetual JS-thread glow loop (Harvest screen)  ·  overdraw + idle JS tax  ·  M
Each card stacks ≥5 `LinearGradient`s + 8 shadow-casting dots across ~5 cards in a horizontal scroll, and the
"current" card runs an infinite `Animated.loop` with `useNativeDriver: false` (`FieldCard.tsx:58-84,142-239`)
— a constant JS-thread tax whenever the Harvest hub is mounted, even idle.
**Fix:** native-driver the opacity glow (or drop on low-RAM); collapse the gradients to a single flat translucent
overlay on Android; drop per-dot shadows (filled vs unfilled color).
**Measure:** Android GPU overdraw debug on Harvest; idle JS FPS before/after.

#### P6. Reader chrome animates layout `bottom` per-frame instead of transform  ·  anim  ·  S
`bottomDockAnimatedStyle` interpolates the `bottom` layout prop (`BibleReaderScreen.tsx:1771-1788`), forcing a
Yoga layout pass each frame on old arch; a `translateY` is already applied alongside it (redundant motion).
**Fix:** express the motion entirely as a `translateY` transform; set the static base `bottom` once.

## Already healthy — do NOT spend effort here
- **FlashList migration done** for book list, chapter grid, translation picker, in-Bible search (Phase 6) — verified
  with sane `estimatedItemSize`. The reader verse list IS virtualized in normal read mode; the `.map()` fallback
  only runs for zero-verse audio-first chapters.
- **Hermes is ON** for Android (`gradle.properties:42`, `build.gradle:177-181`).
- **Cold-start path is excellent:** only one tiny module-scope side effect (`setupNotificationHandler`), splash
  hides on `isReady`, navigator required lazily, all heavy services dynamically imported behind
  `InteractionManager` + 1500ms Android delay (`App.tsx`, `startupService.ts`).
- **MMKV fully applied** to all persisted stores (Phase 29); only boot AsyncStorage touch is the guarded one-time migration.
- **i18n lazy-loads** all non-English locales via dynamic `import()`.
- **Navigation freeze/lazy config is correct** (`freezeOnBlur`, lazy `getComponent`, screens default-detach).
- **No BlurView anywhere** — the usual #1 Android blur offender does not apply.
- **Images are well-sized** (320×180 covers, density variants); the 44MB Bible DB copy is deferred off the
  critical path (but consider shrinking — it grew ~60% to 44MB).
