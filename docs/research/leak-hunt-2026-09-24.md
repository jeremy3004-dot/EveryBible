# Leak hunt: subscriptions, timers and native handles (2026-09-24)

Scope: every `addEventListener` / `addListener` / `subscribe` / `setInterval` /
`setTimeout` / `onAuthStateChange` / `setOnPlaybackStatusUpdate` / `BackHandler` /
`InteractionManager` / `requestAnimationFrame` in `src/` (71 listener/timer call sites
plus 37 `setTimeout`s), and the root `App.tsx`. For each: is there a matching cleanup,
and can a re-render (unstable effect deps) stack duplicates? Code added today was
read line by line.

Method: `grep -rnE` over `src` (tests and fakes excluded), then reading each site and
its owner. Where a site was not already covered by a test that counts listeners,
a mount/unmount-N or install/dispose-N test was added. The React Native stub now
reports `Linking.listenerCount()`, `Dimensions.listenerCount()` and (render harness)
`BackHandler.listenerCount()`, next to the existing `AppState` / `Keyboard` counts
and the Supabase fake's `auth.listenerCount`.

## Leaks found, left to the sessions that own the files

Both files are being changed by other sessions (the reader is being split; the review
screen's voice-note races are already fixed there), so these are recorded, not changed
here. Each was reproduced with a failing render test first (a held `createAsync`, then
unmount or a second tap); the tests are not committed because they need the fix.

## Low-risk notes (not changed)

- `PrivacyLockScreen` checks the PIN in a 0 ms-ish `setTimeout` after `=`; after unmount
  the state updater never runs, so nothing is retained.
- `BibleReaderScreen` swipe guard `setTimeout(150)` only writes a ref.
- `AnnotationActionSheet`'s BackHandler closes over the first render's `onClose`; the
  reader passes a wrapper around a stable `useCallback`, so it is not stale in practice.
- `useAudioPlayer`'s callbacks effect stops the progress-telemetry interval whenever
  `t` changes (language switch) during playback; the next status change restarts it.
  A telemetry gap, not a leak. The listening-telemetry timer is being reworked (shared
  at module level) in another session, as are the `useKeyboardBottomInset` late
  measure and the `privateDataScope` MMKV guards; none of them were changed here.
