# Offline Bible installation

Both catalog text-pack downloads and legacy Supabase verse downloads build a staging SQLite database. Catalog downloads use an operation-owned candidate path, persist a small MMKV recovery journal, and never let a duplicate request replace the current owner. Installation verifies the required reader columns, a representative readable verse, translation identity when known, and expected verse count before registering the installed file. Legacy writers also close their handle when schema creation, transactions, or progress callbacks fail.

Catalog text packs reject unsuccessful HTTP responses. When the catalog supplies `expectedSha256`, it must be a 64-character hexadecimal SHA-256 digest. The installer reads and hashes the staging bytes with the existing pure-JavaScript EL cryptography helpers, including standard Base64 decoding. Verification runs on Hermes without Web Crypto or `atob`. Missing read capability, read errors, invalid encoding, malformed checksums, and checksum mismatches fail the install; none bypass validation. Without a declared checksum, SQLite validation still runs, using the supplied verse count or a minimum of one verse.

A failed download or staging validation only cleans candidate artifacts and leaves the installed Bible intact. Store-managed catalog downloads use a unique candidate final path, so the existing database and SQLite sidecars remain in place until the candidate is registered and read back through the reader. Only then does the store attempt to retire the previous copy. Legacy fixed-path replacement still uses `.rollback` paths; recovery retains that backup until the stronger validation and registration boundary completes. The bundled database schema and version constants do not change.

If filesystem restoration itself fails, the error identifies the preserved rollback path. On the next launch, local recovery runs before a saved translation is classified as missing: it discovers known legacy `.db`/`.rollback` paths even without a journal, reunites sidecars when the activation order proves they belong to the rollback database, preserves ambiguous bytes, and registers a valid recovered final file. An intentional delete writes a tombstone first, so interrupted cleanup cannot resurrect its rollback copy. Recovery is idempotent and does not require the catalog or network. A post-registration cleanup failure leaves the newly verified Bible installed; if the registered-source readback itself fails, the candidate is removed and the prior registered copy is restored when one exists.

Cancel records its request synchronously, calls the Expo resumable task when available, waits for settlement before cleanup or retry, and suppresses late progress, registration, analytics, and picker navigation. Registration is a short non-cancellable phase; the UI keeps the finishing state visible until it completes. Text cancellation is scoped by translation and cannot cancel an audio job. Unknown byte/verse totals use an indeterminate progress bar.

Behavioral tests execute the real installer with native filesystem, SQLite, and Supabase boundaries replaced by small fixtures. They seed an existing Bible and cover failure preservation, staging-first validation, closed handles, replacement/rollback, legacy rollback recovery, cancellation, and hashing without browser globals:

```bash
node --test --experimental-test-module-mocks --import tsx src/services/bible/cloudTranslationService.behavior.test.ts
```
