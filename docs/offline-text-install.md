# Offline Bible installation

Both catalog text-pack downloads and legacy Supabase verse downloads build a staging SQLite database. Catalog downloads use an operation-owned candidate path, persist a small MMKV recovery journal, and never let a duplicate request replace the current owner. Installation verifies the required reader columns, a representative readable verse, translation identity when known, and expected verse count before registering the installed file. Legacy writers also close their handle when schema creation, transactions, or progress callbacks fail.

Catalog installation and recovery also require `PRAGMA quick_check(1)` to return exactly `ok`. This scans the database structure, including overflow pages that a row count and representative chapter read can miss; the argument limits reported errors, not the scan. The check runs on the staging candidate, final-path validation, and interrupted-install recovery. Ordinary chapter reads and startup of already registered, usable packs do not add integrity scans. A matching SHA-256 checksum does not replace the structural check because a provider can publish a malformed database with its matching digest.

Catalog text packs reject unsuccessful HTTP responses. When the catalog supplies `expectedSha256`, it must be a 64-character hexadecimal SHA-256 digest. The installer reads and hashes the staging bytes with the existing pure-JavaScript EL cryptography helpers, including standard Base64 decoding. Verification runs on Hermes without Web Crypto or `atob`. Missing read capability, read errors, invalid encoding, malformed checksums, and checksum mismatches fail the install; none bypass validation. Without a declared checksum, SQLite validation still runs, using the supplied verse count or a minimum of one verse.

A failed download or staging validation only cleans candidate artifacts and leaves the installed Bible intact. Store-managed catalog downloads use a unique candidate final path, so the existing database and SQLite sidecars remain in place until the candidate is registered and read back through the reader. Only then does the store attempt to retire the previous copy. Legacy fixed-path replacement still uses `.rollback` paths; recovery retains that backup until the stronger validation and registration boundary completes. The bundled database schema and version constants do not change.

If the store's final-path validation fails after transfer activation, it closes and removes that operation's unique candidate before retiring the install journal, preserving the prior pack and the original validation error. Cleanup is best effort: a native invalidation or deletion failure is logged and can leave an unreferenced candidate. The existing failure path still retires its install journal; it does not provide durable cleanup retries for that case.

If filesystem restoration itself fails, the error identifies the preserved rollback path. On the next launch, local recovery runs before a saved translation is classified as missing: it discovers known legacy `.db`/`.rollback` paths even without a journal, reunites sidecars when the activation order proves they belong to the rollback database, preserves ambiguous bytes, and registers a valid recovered final file. An intentional delete writes a tombstone first, so interrupted cleanup cannot resurrect its rollback copy. Recovery is idempotent and does not require the catalog or network. A post-registration cleanup failure leaves the newly verified Bible installed; if the registered-source readback itself fails, the candidate is removed and the prior registered copy is restored when one exists.

Registered installed Bibles can be read and searched even when bundled database initialization fails. Pending installation journals are recovered before choosing the source; installed reads do not mark the bundled database ready or prevent a later bundled retry. Missing or corrupt installed files retain their own recovery and error handling.

A startup download of the account's saved Bible only selects it, or its failure fallback, while the reader's local choice and choice stamp remain unchanged and the same account session still owns the request. Choosing another Bible and returning to the original one keeps that newer choice; the completed pack still remains available offline. A sign-out and new login, including to the same account, retires the earlier request. Startup preference uploads retain that captured account through user lookup and row merging.

Bible database handles use independent native connections while retaining the existing JavaScript reader cache and single-flight initialization. Temporary startup probes can close and be collected without releasing a retained reader's binding. The ownership regression models the installed Expo SQLite 16.0.10 Android cache, reference count, and shared-object release separately; it does not establish Hermes garbage-collection timing or the exact native error code. Native cold-launch verification remains a separate check.

When the reader changes translations, including automatic fallback from a missing installed pack, it shows its loading state until the replacement Bible's chapter arrives. Retained text from the previous Bible is never shown under the replacement label. Chapter changes within the same Bible still keep existing text visible without a loading skeleton; a failed replacement load settles to the existing error and retry controls.

Cancel records its request synchronously, calls the Expo resumable task when available, waits for settlement before cleanup or retry, and suppresses late progress, registration, analytics, and picker navigation. The store loads the transfer service before showing the cancellable banner, so an immediate cancel reaches an active transfer. Registration is a short non-cancellable phase; the UI keeps the finishing state visible until it completes. Text cancellation is scoped by translation and cannot cancel an audio job. Unknown byte/verse totals use an indeterminate progress bar.

Behavioral tests execute the real installer with native filesystem, SQLite, and Supabase boundaries replaced by small fixtures. They seed an existing Bible and cover failure preservation, staging-first validation, closed handles, replacement/rollback, legacy rollback recovery, cancellation, and hashing without browser globals:

```bash
node --test --experimental-test-module-mocks --import tsx src/services/bible/cloudTranslationService.behavior.test.ts
```

Deletion recovery owns only the artifact paths captured by its tombstone. If native removal fails and the user installs a newer pack at a unique path, cold-start recovery preserves that installed pack and independently recovers its candidate journal. The old tombstone remains until its captured artifacts are removed; an install actually captured by the deletion is still prevented from being resurrected.
